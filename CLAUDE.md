# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

One **receiver** on the PC and three independent **senders** (phones), all speaking the same wire protocol (PMP v1). The phone becomes a Wii-style motion pointer, a virtual Wiimote for Dolphin (via DSU/cemuhook), or a Wii U GamePad for Cemu (with the GamePad's second screen streamed back to the phone).

| Component | Path | Stack |
|---|---|---|
| Receiver (Windows + Linux) | `desktop/` | Rust, egui/eframe |
| Shared PMP codec | `pmp/` | Rust, no deps, `#![forbid(unsafe_code)]` |
| Shared DSU/cemuhook server | `dsu/` | Rust, `crc32fast` only |
| DSU JNI bridge for Android | `dsu-android/` | Rust cdylib → `libpepomote_dsu.so` |
| Android sender | `android/` | Kotlin, Jetpack Compose |
| iOS/iPadOS sender | `ios/` | Swift, SwiftUI (project generated by XcodeGen) |
| Linux-phone sender | `mobile-linux/` | Rust, egui on Wayland |
| Protocol spec + golden vectors | `protocol/` | Markdown + `.hex` |

## Language conventions

Code comments, `docs/`, `protocol/`, log lines, `--diag` output and **commit messages are all in Spanish**. `README.md` is English; `README.es.md` is its Spanish twin — keep both in sync. User-facing UI strings ship in Spanish *and* English, with parity enforced by tests (see i18n below).

## Build and test

Rust (receiver, codec, Linux-phone sender) — each is a standalone crate, no workspace:

```powershell
cd desktop ; cargo build --release          # produces PepoMote.exe / PepoMote
cd desktop ; cargo test --release
cd pmp ; cargo test                          # codec vs golden vectors
cd dsu ; cargo test                          # DSU server + INI templates
cd mobile-linux ; cargo build --release ; cargo test
```

Single Rust test: `cargo test --release pointer::engine::tests::nombre` (all Rust tests are inline `mod tests`; there is no `tests/` dir). Linux build deps: `libgtk-3-dev libxcb-render0-dev libxcb-shape0-dev libxcb-xfixes0-dev libxkbcommon-dev libssl-dev libasound2-dev libudev-dev` (receiver), `libxkbcommon-dev libwayland-dev libxcb-*-dev libgl1-mesa-dev` (mobile-linux).

## Architecture

### The protocol is the contract

`protocol/PROTOCOL.md` is the source of truth. If code and that document disagree, **the document wins**. Three independent codecs implement it and are all tested against the same golden hex vectors in `protocol/vectors/`:

- `pmp/src/lib.rs` — pulls vectors with `include_str!`; shared by the receiver and the Linux-phone sender
- `android/.../net/PmpCodec.kt` — vectors wired in as test resources (`resources.srcDir("../../protocol/vectors")` in `app/build.gradle.kts`)
- `ios/PepoMote/Net/PmpCodec.swift` — vectors are a test-bundle resource (`ios/project.yml`)

Changing the wire format means updating the spec, the vectors, and all three codecs plus their tests together. Within `pv=1` only **additive** changes are allowed: the 80-byte Wii U extension block is gated behind `FLAG_EXT` and is only emitted after the receiver has confirmed `cemu` mode, so an old receiver never sees a packet that isn't 72 bytes. A layout change means `pv=2`.

Ports and channels: UDP **26761** = hot telemetry (`INPUT` at sensor rate, ≤250 Hz, full button state every packet so a dropped packet never sticks a button) · TCP **26761** = control channel, one line-delimited JSON message per line · a *separate* TCP connection on the same port = GamePad screen streaming (JPEG frames, one-byte ack per frame, one image in flight) · UDP **26760** = the DSU/cemuhook server Dolphin and Cemu connect to.

### Receiver (`desktop/`)

`main.rs` is the wiring diagram: panic hook → CLI short-circuits (`--diag`, `--replay`, `--dolphin-dirs`) → singleton lock → `state::SharedState` → DSU server → `ScreenHub` → net threads → auto-mode watcher → egui window. Everything works **headless**; the window is just a view over the shared state (`PEPOMOTE_NO_UI=1` on Linux, `--minimized` on Windows).

- `net/control.rs` — one thread per phone, up to 4 sessions. Slot 0 is Player 1 and is the only one allowed to change the mode. Wiimotes take slots from 0 up, Nunchuks from 3 down, and the *i*-th of each are paired.
- `net/telemetry.rs` — the hot path: UDP `INPUT` → pointer engine (slot 0 only) and DSU push (every slot). Keep it allocation-light; the DSU streaming happens inline here rather than on the DSU thread specifically to avoid added latency.
- **Modes**: `pointer` injects into the OS. `dolphin` and `cemu` inject *nothing* — the entire state goes out the DSU server instead. `auto_mode.rs` can flip the mode from the PC side when an emulator opens/closes; its rules are pure functions and tested there.
- `pointer/engine.rs` — world-anchored absolute aiming. The gyro drives the cursor; the quaternion only *anchors* the internal state when the phone is still, silently. This makes it roll-invariant (rotating the phone while aiming doesn't move the cursor). Read its module doc before changing anything here; `one_euro.rs` deliberately shares one adaptive cutoff across both axes so diagonals stay straight.
- `dsu/src/mapping.rs` — the **only** place axis signs and units are converted (Android gives m/s² and rad/s, DSU wants g and °/s). Fix inverted axes here, nowhere else. It lives in its own crate because the Android app serves DSU too (see below); `desktop/src/dsu.rs` is just the receiver's adapter around it (loopback bind + port eviction).
- `dsu/src/ini.rs` — the Dolphin `WiimoteNew.ini` / `DSUClient.ini` templates, shared by `desktop/src/dolphin.rs` (which writes them) and the Android app (which can only display them).
- `input/` — Windows: `SendInput`. Linux: wlroots virtual pointer/keyboard first (Sway, Hyprland, niri… no permissions needed), falling back to uinput on GNOME/KDE/X11. `fixes.rs` self-repairs uinput permissions and the firewall through a single `pkexec` prompt.
- `dolphin.rs` / `cemu.rs` write the emulators' own config files. **Never write while the emulator is running** — it rewrites its config on exit and would clobber ours; pending writes are queued and applied when it closes, and any replaced file gets a `.pepomote.bak`.

### The three senders mirror each other

Android, iOS and Linux-phone are three implementations of one design. The pure logic is deliberately duplicated per platform with matching names and semantics, each with its own unit test — a behavior change usually has to land in all three:

| Logic | Android | iOS | Linux phone |
|---|---|---|---|
| Codec | `net/PmpCodec.kt` | `Net/PmpCodec.swift` | `pmp` crate |
| Press latch (≥70 ms on the wire) | `control/PressLatch.kt` | `Control/PressLatch.swift` | `src/buttons.rs` |
| Stick / text mapping | `control/StickMap.kt`, `TextInput.kt` | `Control/StickMap.swift`, `TextInput.swift` | `src/ui/`, `src/ui/text.rs` |
| Which screen to show | `service/Route.kt` | `Service/Route.swift` | `src/app.rs` |
| Reconnect backoff | `service/Reconnect.kt` | `Service/Reconnect.swift` | `src/link.rs` |
| Screen-channel framing | `net/ScreenFrames.kt` | `Net/ScreenFrames.swift` | `src/screen.rs` |

The link lifetime differs by platform and that's intentional: Android keeps it in a foreground service with a wakelock + low-latency WifiLock; iOS can only run while on screen; Linux-phone holds the screen awake through a `gnome-session-inhibit`/`systemd-inhibit` child process.

Android has one extra mode with no PC in it at all — **"Dolphin en Android"** (`docs/DOLPHIN-ANDROID.md`): the phone hosts the DSU server itself on `0.0.0.0:26760` and Dolphin on a *second* Android device connects over Wi-Fi. It reuses `MotionEngine` untouched by swapping its `onPacket` sink to push the same PMP `INPUT` bytes across JNI into the `dsu` crate (`dsu-android/`), so there is no second codec and the golden vectors still cover the path. `DsuForegroundService` mirrors `LinkForegroundService`'s lifetime handling.

Up to **four** phones can play at once in that mode (*"la party"*, `protocol/PROTOCOL.md` §7): each still serves its own DSU on its own IP, and one acts as host purely to collect the others' IPs — it shows a QR, they join over TCP 26761, and it generates the two INIs naming everyone. Game traffic never passes through the host. Player numbers are **positional** (`net/PartyRoster.kt`) because `dsu/src/ini.rs` names the servers `PepoMote-P<n>` by position: if the two ever disagreed, the phone's screen and Dolphin's device list would name the same phone differently. The transport is `net/Party.kt`, which builds its JSON by hand — `org.json` lives in `android.jar` and throws in JVM unit tests.

Sensors also differ: Android gets `GAME_ROTATION_VECTOR` and a HAL-calibrated gyro for free. The Linux phone gets neither, which is why `mobile-linux/` carries three modules the others don't need — `fusion.rs` (Madgwick, produces the same quaternion), `bias.rs` (gyro bias at rest, or the pointer drifts) and `calib.rs` (six guided poses to deduce axis signs).

`mobile-linux/src/main.rs` includes `desktop/src/{theme,icon,i18n}.rs` via `#[path]` so both egui apps share one palette, icon and i18n engine. Editing those three files changes both apps — both must still compile.

### i18n

- Rust apps: `src/strings.rs` holds `(key, español, english)`; `tr!("key")` / `tr!("key", a, b)` with `{0}` holes. Tests assert every used key exists, none is unused, and holes match.
- Android: `res/values/strings.xml` (es) + `res/values-en/strings.xml` (en), enforced by `StringsParityTest`.
- iOS: `Resources/{es,en}.lproj/Localizable.strings`, enforced by `StringsParityTests`.

Only what the user sees is translated. Protocol, logs and `--diag` stay Spanish.

## Local e2e and debugging

`desktop/e2e/` runs Python 3 scripts (no deps) against a **real** receiver started in isolation so it touches neither your config nor Dolphin/Cemu:

```
PEPOMOTE_CONFIG_DIR=<dir>\config  PEPOMOTE_DOLPHIN_DIR=<dir>\dolphin  APPDATA=<dir>\appdata
PEPOMOTE_PORT=26771  PEPOMOTE_DSU_PORT=26770
PEPOMOTE_PAIR_CODE=1234  PEPOMOTE_ASSUME_EMULATOR_CLOSED=1  PEPOMOTE_NO_TRAY=1
```

Then `python e2e_cemu.py <appdata>` (Wii U profiles + PadData), `e2e_nunchuk.py`, `e2e_screen.py`, or `cemu_live.py` (simulated phone against your normal receiver). Build the e2e receiver with `CARGO_TARGET_DIR=target-e2e` so it doesn't fight your normal build. Linux/Wayland: `bash desktop/e2e/e2e_wayland.sh` boots a headless `sway` with `wev` and asserts real cursor/click/key events — this is what CI runs. See `desktop/e2e/README.md`.

Other switches: `PEPOMOTE_DEBUG=1` (verbose logging), `PEPOMOTE_RECORD=<file>` + `PepoMote --replay <file>` (capture a real gesture and push it through the pointer engine offline, CSV to stdout), `PepoMote --diag` (diagnostic report), `PepoMote-Mobile --sensors` / `--pair HOST CODE`.

## Releasing

The version number lives in **seven** places and they must move together: `desktop/Cargo.toml`, `pmp/Cargo.toml`, `dsu/Cargo.toml`, `dsu-android/Cargo.toml`, `mobile-linux/Cargo.toml` (plus their `Cargo.lock`s), `android/app/build.gradle.kts` (`versionCode` *and* `versionName`) and `ios/project.yml` (`MARKETING_VERSION`). Commit, then `git tag vX.Y.Z && git push origin main --tags` — `release.yml` builds every artifact, generates `SHA256SUMS.txt` and `altstore.json`, and publishes the GitHub Release. The `.deb` version must be *strictly greater* than the last published one or apt won't offer the update. Details in `docs/RELEASE.md`.

## Legal constraint

Zero Nintendo assets, trademarks, fonts or sounds — this is deliberate and load-bearing. The app icon is drawn procedurally (`desktop/src/icon.rs`), the chimes are synthesized at runtime (`desktop/src/sound.rs`) or generated by `assets/sounds-src/gen_sounds.py`, and "Wii"/"Wii U" are used only nominatively to describe Dolphin/Cemu compatibility. Don't introduce a third-party asset here. See `docs/LEGAL.md`.
